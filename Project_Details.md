# Full Project Documentation: SkillNear

## 1. Project Overview
**SkillNear** is a premium, hyperlocal service marketplace platform designed to bridge the gap between skilled local professionals and people in need of home services. It operates as a digital directory and service booking ecosystem, allowing users to find, communicate with, and hire experts like electricians, tutors, salon professionals, and more, within their immediate vicinity.

### What is this project?
SkillNear is a full-stack MERN (MongoDB, Express, React, Node.js) application that facilitates service discovery. It features a modern, Urban Company-inspired interface with real-time capabilities for communication and location-based filtering.

### How does it benefit?
- **For Users:** Quick access to trusted service providers, real-time chat for price negotiation/inquiries, and location-based results to ensure faster response times.
- **For Providers:** Digital visibility for small-scale skilled workers, a professional profile to showcase their work, and a direct channel to acquire customers without high platform commissions.
- **For the Community:** Boosts the local economy by promoting "Skill Near You" (Hyperlocal focus).

### Current Situation
The project is currently a fully functional MVP (Minimum Viable Product) with a polished frontend, secure backend authentication, real-time messaging, and location-aware service filtering. It uses professional design patterns, animations, and a responsive layout optimized for both desktop and mobile users.

## 4. Deep Dive: Core Implementations

### A. How Current Location is Detected
SkillNear uses a hybrid approach to location detection to ensure accuracy and user control.

**Implementation Logic:**
1.  **Geolocation API:** The browser's `navigator.geolocation` API is used to retrieve the user's longitude and latitude.
2.  **Reverse Geocoding:** The coordinates are sent to a reverse geocoding service (Nominatim OpenStreetMap) to convert them into readable address components (City, State, Pincode).
3.  **State Management:** The detected location is stored in a global state (Zustand) and persisted to the backend database if the user is logged in.

**Code Snippet (Logic):**
```javascript
const handleAutoDetect = () => {
    navigator.geolocation.getCurrentPosition(async (pos) => {
        const { latitude, longitude } = pos.coords;
        const res = await fetch(`https://nominatim.openstreetmap.org/reverse?format=json&lat=${latitude}&lon=${longitude}`);
        const data = await res.json();
        // Extract city, state, pincode and update state
        setLocation({ city: data.address.city, state: data.address.state, pincode: data.address.postcode });
    });
};
```

### B. How the Chat Feature Works
The chat system is built for real-time interaction between a user and a service provider.

**Core Mechanism:**
1.  **WebSockets (Socket.io):** Unlike standard HTTP requests, WebSockets maintain an open connection, allowing instant message delivery.
2.  **Room IDs:** Each conversation has a unique `roomId`. For direct chats, the ID is generated by sorting the IDs of the two users (e.g., `direct_userId1_userId2`).
3.  **Events:** 
    - `setup`: Registers the user's connection.
    - `joinRoom`: Places the user in a specific chat room.
    - `sendMessage`: Sends a message to the server, which then emits it to the other user in the room.
    - `typing`/`stopTyping`: Notifies the other user when someone is typing.

**Implementation Highlights:**
- **Optimistic Updates:** Messages appear instantly in the UI.
- **Persistence:** Messages are saved in MongoDB so they can be retrieved later.
- **Online Indicators:** Real-time tracking of which users are currently connected.

## 6. Interview Questions (20 Q&A)

### Technical (Stack Specific)
1. **Q:** Why did you choose Vite over Create React App?
   **A:** Vite is significantly faster for development due to ESBuild and handles module updates (HMR) more efficiently.
2. **Q:** How do you handle authentication securely in this project?
   **A:** Using JWT (JSON Web Tokens) stored securely, with passwords hashed using Bcrypt on the backend.
3. **Q:** Explain the benefit of using Zustand over Redux.
   **A:** Zustand is more lightweight, has less boilerplate, and uses a simpler hook-based API which is perfect for a fast-paced project like this.
4. **Q:** How does Socket.io differ from traditional HTTP requests?
   **A:** HTTP is request-response based, while Socket.io provides a full-duplex bi-directional communication channel (WebSocket).
5. **Q:** How do you ensure your MongoDB queries are efficient?
   **A:** By using indexing on frequently queried fields like `category` or `location.pincode` and using Mongoose lean() where applicable.
6. **Q:** What is the role of Multer in your project?
   **A:** Multer acts as middleware for handling `multipart/form-data`, primarily used for uploading service images to the server before sending them to Cloudinary.
7. **Q:** How do you handle global CSS variables in your project?
   **A:** I use a central `index.css` with a `:root` selector to define design tokens (colors, spacing, shadows) for consistency.
8. **Q:** How does reverse geocoding work in your location detection feature?
   **A:** It takes numerical coordinates (lat/lng) and queries an external API (OSM) to return a human-readable address.
9. **Q:** What is the purpose of React-Hot-Toast in your UI?
   **A:** To provide non-intrusive, professional notifications for user actions like "Location Saved" or "Login Failed".
10. **Q:** How do you handle file uploads to Cloudinary securely?
    **A:** By using environment variables for API keys and performing the upload through a protected backend route.

### Project Specific
11. **Q:** What was the biggest challenge in implementing the Chat feature?
    **A:** Synchronizing the "typing" state and ensuring room-based message isolation so messages don't leak into other chats.
12. **Q:** How do you handle mobile responsiveness?
    **A:** I use a combination of CSS media queries and conditional React rendering based on the window width.
13. **Q:** What happens if a user denies location access?
    **A:** The application provides a manual location picker (State/City/Pincode) as a fallback.
14. **Q:** How is the "Quick Book" feature different from a normal booking?
    **A:** It bypasses long forms and uses pre-saved user details for an instant service request.
15. **Q:** Why did you use Leaflet for maps?
    **A:** It is an open-source, lightweight alternative to Google Maps that is highly customizable and doesn't require expensive API keys.
16. **Q:** How do you manage the "Online/Offline" status of users?
    **A:** The backend tracks active Socket connections and broadcasts the list of active User IDs to all connected clients.
17. **Q:** What design system did you follow?
    **A:** A custom design system following modern UX trends: glassmorphism, rounded corners (radius-lg), and a clean "Inter" font typography.
18. **Q:** How do you prevent unauthorized users from accessing the Provider Dashboard?
    **A:** Using a protected route wrapper on the frontend and an Auth middleware on the backend that verifies the JWT role.
19. **Q:** How do you handle search queries to prevent many API calls?
    **A:** In a production environment, I would use debouncing on the search input, but currently, it uses a form submit trigger.
20. **Q:** How would you scale this project?
    **A:** By implementing Redis for caching, load balancing the Express server, and optimizing MongoDB with Sharding for different geographic regions.
